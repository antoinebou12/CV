ipc-toolkit: Collision queries as a library boundary

ipc-toolkit provides geometric building blocks for contact-aware simulation. This fork contains collision meshes, broad-phase candidates, continuous collision detection and contact-related energies. An external simulation still owns its time stepping and solve loop.

4. Features and components 2

Geometry and collision queries
ipc.hpp accepts a CollisionMesh and vertex positions for intersection and collision-free-step queries. Broad-phase and narrow-phase CCD implementations are explicit parameters with defaults, separating candidate discovery from detailed tests.
Contact calculations
The source tree separates distance, barrier, friction, tangent and potential modules. These components support a caller’s objective and derivatives; they do not automatically integrate an entire physical scene.

7. Algorithm

7.1. Problem

Decide whether a CollisionMesh at given vertex positions intersects, or whether a proposed vertex displacement stays collision-free, so a contact-aware simulator can query geometry without owning the full time-step loop.

7.2. Inputs

A CollisionMesh plus current (and optionally proposed) vertex positions; broad-phase and narrow-phase CCD strategies are explicit parameters with defaults.

7.3. Outputs

Intersection or collision-free-step answers, plus contact-related quantities (distances, barriers, friction helpers) consumed by the caller’s objective — not a full scene solve.

7.4. Pseudocode (source-backed)

given mesh M, positions x, optional next positions x'
if has_intersections(M, x): report contact candidates
if not is_step_collision_free(M, x, x'): reject or shorten step
else: assemble contact energies/derivatives for the caller’s solver
  1. 1. Build or accept a collision mesh

    The library expects a CollisionMesh that separates geometry from the caller’s simulation state.

  2. 2. Broad-phase candidates

    Candidate pairs are discovered with an explicit broad-phase strategy before expensive narrow tests.

  3. 3. Narrow-phase CCD / intersection

    ipc.hpp entry points test intersections at a configuration or whether a displacement remains collision-free.

  4. 4. Contact quantities for the solver

    Distance, barrier, friction and related modules supply values and derivatives; the external simulation still owns time stepping.

No asymptotic complexity claim is published in this fork’s inspected headers; cost depends on mesh size, broad-phase choice and CCD settings used by the caller.

12. Glossary

Repository

The versioned source files, configuration, and history of a project.

README

The repository’s entry document, usually covering its purpose and initial setup.

Dependency

A library, tool, or service that another component needs to build or run.

Container

An isolated process environment created from an image. Persistent data needs storage outside the container’s disposable filesystem.

Published port

A host port mapped to a service’s container port. Publishing a port can expose that service beyond its container network.

Build

The steps that turn source files and dependencies into a runnable program or distributable artifact.

Continuous integration

Automated checks that run when source changes, such as building, testing, and linting. Passing checks cover only what those checks exercise.

GPU

A processor designed for parallel workloads, including graphics rendering and many numerical operations.

Mesh

A surface represented by vertices and connected elements, often triangles. Its geometry is distinct from its material or texture.

Continuous collision detection

A test for contact during the motion between two states, rather than only at the sampled endpoints.

Fork

A separate repository derived from another project. A change in a fork is not automatically a change in the upstream project.
