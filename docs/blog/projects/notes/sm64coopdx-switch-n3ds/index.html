Prerequisites and first run

Requirements

docs/SWITCH_INSTALL.md

  • A homebrew-capable Nintendo Switch with a current Homebrew Menu setup.
  • The SM64CoopDX Switch distribution ZIP.
  • Your own legally obtained North American Super Mario 64 ROM matching the SHA-1 recorded in sm64.us.sha1 in the source repository. The ROM is copyrighted data and is not included in the distribution. Do not download, upload, or redistribute it.
Read the full instructions ↗

Install

docs/SWITCH_INSTALL.md

  1. Shut down the Switch before removing its SD card, or use a safe USB/FTP transfer method.
  2. Extract the distribution ZIP directly to the root of the SD card. It creates switch/sm64coopdx/.
  3. Copy your ROM to switch/sm64coopdx/baserom.us.z64.
  4. Confirm this layout:
  5. Put the SD card back in the Switch and start the Homebrew Menu in full application mode. With common Atmosphere setups, hold R while launching an installed game until Homebrew Menu opens. Album/applet mode has less memory and is not recommended.
  6. Launch SM64CoopDX.
Read the full instructions ↗
Operations and troubleshooting

Updating

docs/SWITCH_INSTALL.md

Replace sm64coopdx.nro, icon.jpg, and lang/ with the files from the new distribution. Keep your private baserom.us.z64, mods, saves, configuration, and logs.
Read the full instructions ↗

Troubleshooting and logs

docs/SWITCH_INSTALL.md

  • If startup reports a missing or invalid ROM, verify its filename, region, and SHA-1.
  • If the game freezes or runs out of memory, confirm it was launched in full application mode rather than Album/applet mode.
  • Private-lobby passwords use the in-game Switch keypad; that flow should not open the native software keyboard.
  • Switch public discovery uses the Android lobby list. It will not show lobbies published only in the desktop namespace.
  • If a particular server rejects the Switch build, share switch-coopnet-identity.txt with that server’s operator; do not replace the genuine hash with another executable’s identity.
  • Runtime diagnostics are written under switch/sm64coopdx/logs/, including startup.log, coopnet.log, checkpoints, and exception.log. When sharing diagnostics, remove lobby passwords, TURN credentials, and other private information first.
Read the full instructions ↗

Features and components 2

Shared runtime and backends
src/pc separates controller, audio, graphics, networking and platform code. Porting work can replace a backend while keeping shared game behavior. Build flags and target makefiles determine which implementations are linked.
The platform probe
Makefile.switch-platform compiles a probe with Switch lifecycle, input and crash-log code, then packages an NRO using devkitPro tools. Its source list is deliberately smaller than the full game’s build.

Glossary

Repository

The versioned source files, configuration, and history of a project.

README

The repository’s entry document, usually covering its purpose and initial setup.

Dependency

A library, tool, or service that another component needs to build or run.

HTTP

A request-and-response protocol used by browsers and web services. A method, path, headers, and optional body describe a request.

Session

State kept across related requests, often to track a signed-in user. Authentication and permission checks remain separate concerns.

Container

An isolated process environment created from an image. Persistent data needs storage outside the container’s disposable filesystem.

Published port

A host port mapped to a service’s container port. Publishing a port can expose that service beyond its container network.

CLI

A text interface in which commands and arguments select operations. Exit codes let scripts detect success or failure.

Build

The steps that turn source files and dependencies into a runnable program or distributable artifact.

GPU

A processor designed for parallel workloads, including graphics rendering and many numerical operations.

Shader

A program executed at a stage of a graphics or compute pipeline, for example to transform vertices or calculate pixel colors.

Backend

An implementation behind a shared interface. Depending on context, it can mean a server-side service or a graphics, input, or storage implementation.

Firmware

Software running on a device or microcontroller to control its hardware and communication.

Fork

A separate repository derived from another project. A change in a fork is not automatically a change in the upstream project.
